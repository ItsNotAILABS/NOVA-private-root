# NOVA Full Sphere Architecture (Enterprise Comprehensive)

This document is the reusable, non-collapsing architecture map for NOVA/PARALLAX/SOVEREIGN-style builds.
It is intentionally explicit about:

- what each entity *is* (ontology),
- who can change what (authority),
- how information moves between layers and rings (transfer),
- and what must be built first before anything else (gates).

---

## 1) Core Rule: Non-Collapse

Never collapse these categories:

1. **Absolute** != Law
2. **Law** != Model
3. **Model** != Engine
4. **Engine** != Core
5. **Core** != Module
6. **Lab** != Workforce
7. **Product** != Organism Truth

If these collapse, the architecture becomes linear and loses sovereignty.

---

## 2) Three-Axis View (Required in all planning)

### Axis A — Ontology (what something is)

Use the unified Tier taxonomy:

- **T0** Absolutes (discovered truths)
- **T0.5** Encoding bridge (`phi.mo`, `phi.ts`)
- **T1** Laws (Medina registry)
- **T2A** Backend substrate (alive before backend logic)
- **T2B** Frontend substrate (alive before frontend logic)
- **T3** Cores
- **T4A** Internal engines (inside cores)
- **T4B** Sovereign engines (alongside cores)
- **T5** Medina models
- **T6** Backend modules
- **T7A** Frontend logic modules
- **T7B** Frontend kernels (intelligence surfaces)
- **T8** Frontend grouping modules
- **T9** Swarm federation

### Axis B — Sovereignty (who owns truth)

- **Doctrine authority**: Absolutes/laws and their change controls
- **Core A authority**: runtime organism truth and acceptance gates
- **Intrinsic labs authority**: organism self-improvement proposals
- **Core B authority**: workforce build/release proposals
- **Product authority**: external projection only (zero exposure enforced)

### Axis C — Lifecycle (how changes move)

Discover -> Encode -> Constrain -> Run -> Improve -> Industrialize -> Project -> Replay -> Reinforce.

## 3) Ring Architecture (inside -> outside)

This is the corrected full-sphere ring order.

### R0: Crown Fundamentals Ring

- Absolutes and encoded constants (`phi.mo`, `phi.ts`)
- No direct business logic.
- This is inherited, not "implemented from scratch."

### R1: Doctrine and Law Ring

- Medina law registry
- Law enforcement function declarations
- Doctrine fingerprint and law-change governance

### R2: Substrate Language Ring

- Backend substrate + frontend substrate
- Canonical type contracts (`types.mo`, `types.ts`)
- Beat and field coupling discipline

### R3: Runtime Intelligence Ring (Core A Domain)

- Beat loop, coherence/drift field, arbitration, reinjection, continuity
- Sovereign runtime truth ownership
- Includes cores and their internal/sovereign engines through governed execution

### R4: Intrinsic Labs Ring (Inside Organism)

- Labs that improve organism intelligence from within
- Coherence tuning, drift hardening, memory quality, defense adaptation
- Cannot bypass Core A acceptance gates

### R5: Industrial Workforce Ring (Core B Domain)

- Internal AI employees for planning/build/testing/release
- Uses organism truth snapshots and writes proposals
- Build factory for company-level execution

### R6: Product Projection Ring

- Public products, enterprise products, APIs, operator experiences
- Controlled projections of approved capabilities
- Can include workforce-as-product, but not doctrine internals

### R7: External Ecosystem Ring

- Customer environments, partner systems, device networks, world integrations
- Swarm federation and franchise/external expansion

## 4) Twin Core Strategy (Execution Overlay)

Twin Core is an overlay over rings/tiers, not a replacement.

### Core A — Runtime Intelligence Core

Scope:
- R3 + governance over R4 inputs

Responsibilities:
- Runtime truth, law-first actuation, deterministic arbitration
- Continuity/replay integrity, sovereign acceptance decisions

### Core B — Workforce Orchestration Core

Scope:
- R5 and controlled interactions with R3/R4

Responsibilities:
- Build planning, implementation coordination, verification, release orchestration
- Artifact/report pipelines and productization workflows

Boundary law:
- Core B can propose; Core A authorizes runtime truth changes.

## 5) Medina Models Placement (No ambiguity)

Medina models exist in three simultaneous forms:

1. **M0 Archetype** (doctrine meaning)
2. **M1 Type Contract** (`types.mo`/`types.ts` shared shapes)
3. **M2 Runtime Instance** (per-beat state records)

Rule:
- If a structure is used only in one local context, it is not a sovereign model.

## 6) Transfer Protocol (Layer-to-Layer and Ring-to-Ring)

### T01: Absolutes -> Doctrine
- discovered truth is encoded into enforceable law intent

### T12: Doctrine -> Language
- law constraints become model contract constraints and gate IDs

### T23: Language -> Runtime
- Core A execution accepts only contract-valid packets

### T34: Runtime -> Intrinsic Labs
- deficits and stress signatures generate self-improvement work

### T43: Intrinsic Labs -> Runtime
- proposals return through law/arbitration acceptance

### T35: Runtime -> Workforce
- governed truth snapshots and priorities become workforce tasks

### T53: Workforce -> Runtime
- workforce submits candidate changes for acceptance

### T56: Workforce -> Products
- approved capabilities industrialized into product surfaces

### T67: Products -> Ecosystem
- external deployment, partner integration, field operation

### T70: Ecosystem -> Doctrine Review
- replay evidence influences doctrine only through controlled governance

## 7) Enterprise Build Order (Hard Gates)

### Gate A: Core A Readiness (must pass first)

1. Deterministic beat
2. Bounded coherence/drift under stress
3. Law-before-actuation everywhere
4. Deterministic arbitration + reserve lineage
5. No-drop reinjection
6. Replay chain reconstructable

If Gate A fails:
- Core B has observe-only permissions.

### Gate B: Core B Activation

1. Contract compatibility with Core A
2. Law fit and security checks
3. Controlled write channels and rollback hooks
4. Audit/replay for build actions

### Gate C: Product Exposure

1. Zero-exposure filters verified
2. Public outputs numeric/proof-safe only
3. Owner-only surfaces protected
4. Incident and rollback controls active

## 8) Internal Labs vs Industrial Workforce

### Intrinsic Labs (R4)
- improve organism itself
- examples: coherence lab, drift lab, memory lab, defense adaptation lab

### Industrial Workforce (R5)
- build company outputs
- examples: architecture planner, code integrator, validator, release coordinator

### Workforce-as-Product (R6)
- externalized projection of selected R5 capabilities only

---

## 9) Reuse Pattern Across Builds

Each new build (NOVA/PARALLAX/SOVEREIGN variant) should be:

`Shared Absolutes + Shared Laws + Shared Model Language + Core A instance + Core B adapter + Domain Rings`

This preserves the crown core and prevents re-thinking fundamentals from zero.

---

## 10) Minimal Governance Matrix (Who can write)

- **Doctrine Registry**: Doctrine authority only
- **Type Contracts**: Platform model authority + doctrine checks
- **Runtime Truth**: Core A only
- **Intrinsic Lab Proposals**: R4 owners, accepted by Core A
- **Workforce Proposals**: Core B owners, accepted by Core A (runtime) or Product authority (non-runtime)
- **Public Surfaces**: Product authority under Zero-Exposure policy

---

## 11) Operating Law (single sentence)

Doctrine gives purpose, model language gives shared meaning, Core A gives runtime truth, intrinsic labs give self-evolution, Core B gives industrial execution, and products give controlled external expression.
