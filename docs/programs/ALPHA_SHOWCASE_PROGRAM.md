# ITSNotAI Labs Alpha Showcase Program

## Mission

Convert the current repository ecosystem from a collection of ambitious technical assets into a coherent, testable, investor-ready, developer-ready, and operator-ready alpha platform.

The showcase is not a cosmetic layer. Every visual, diagram, dashboard, demo, benchmark, and narrative must point to a runnable system, a verifiable receipt, a real workflow, or an explicitly labeled prototype.

## Program invariant

Every showcased capability must be classified as one of:

- **LIVE** — deployable and tested in the target environment.
- **ALPHA** — runnable end to end with known limitations.
- **PROTOTYPE** — implementation exists but lacks production guarantees.
- **RESEARCH** — architecture, paper, or benchmark without a production runtime claim.
- **PLANNED** — roadmap item with no implementation claim.

No repository may display fictional uptime, fictional process state, fictional production security, or simulated hardware as live infrastructure.

## Major program moves

## Move A — Establish a canonical portfolio registry

Create one machine-readable registry describing every active repository, its role, status, owner, runtime, deployment target, security posture, test posture, public/private boundary, and relationship to other repositories.

Required outputs:

- `portfolio/registry.json`
- `portfolio/dependency-graph.mmd`
- `portfolio/status-matrix.md`
- automated stale-claim detection
- repository naming and archive recommendations

The registry becomes the source for the website, README status tables, roadmap, release notes, and alpha command center.

## Move B — Build the Golden Alpha Path

The first complete showcase path must connect:

1. PhoneAI operator surface
2. canonical MCP initialization and discovery
3. governed tool invocation
4. NOVA agent routing
5. MedinaMemorySystems context retrieval
6. AURO model execution
7. result and policy receipt
8. visible operator result

The Golden Alpha Path is successful only when a clean machine can install, launch, execute one workflow, verify its receipt, and replay the result from documentation.

## Move C — Create a shared trust and execution substrate

All physical, financial, remote-control, and high-impact execution surfaces must inherit a single trust layer:

- authenticated agent identity
- authenticated device identity
- signed session challenge
- proposal-bound approval
- approval expiry and threshold
- atomic persistent nonce consumption
- durable receipt chain
- schema enforcement
- timeout enforcement
- resource and value limits
- revocation
- audit export

This substrate should be implemented once and consumed by NOVA IoT MCP, PhoneAI, ForgeBridge-MCP, PARALLAX, OnChain agents, and connector services.

## Move D — Separate model runtime from cognition runtime

AURO owns model execution concerns:

- model loading
- inference scheduling
- KV-cache policy
- quantization
- provider compatibility
- local/native serving
- evaluation and cost measurement

NOVA and Chimeria own cognition concerns:

- canonical state
- salience
- memory gates
- recurrence
- consequence
- adaptation
- identity
- action arbitration

This boundary prevents orchestration code, model-serving code, and organism-state code from collapsing into one untestable runtime.

## Move E — Turn memory into infrastructure

MedinaMemorySystems should become a stable service boundary with:

- typed memory records
- lineage and provenance
- episodic, semantic, procedural, and working memory
- compression and retention policies
- low-memory pressure modes
- snapshot and restore
- named-vector and multi-vector support
- retrieval evaluation
- per-agent and shared namespaces
- durable conflict and unresolved-tension records

The first adapter targets should be SQLite/local files, Qdrant, and an interchangeable large-scale vector backend.

## Move F — Build a real alpha evidence system

Every alpha workflow should emit a standard evidence bundle:

- run manifest
- environment fingerprint
- inputs and policy hashes
- model and tool versions
- execution timings
- measured cost
- output digest
- receipt-chain head
- test result summary
- screenshots or video capture references

This should be reusable across MESIE benchmarks, AURO inference, NOVA tools, PARALLAX workflows, MCP calls, and OnChain deployments.

## Move G — Build the showcase as generated infrastructure

The showcase should be generated from repository facts rather than manually maintained claims.

Generated outputs:

- portfolio homepage
- product family pages
- architecture maps
- live status matrix
- benchmark cards
- security posture cards
- demo gallery
- release timeline
- dependency graph
- claim-to-evidence index

Visual assets must live in repositories and be reproducible from source diagrams, scripts, or recorded demos.

## Move H — Create one external-radar adoption process

The external repo radar becomes an engineering input, not a reading list.

For each tracked upstream project, record:

- signal date
- upstream release or commit
- affected internal systems
- adoption decision
- compatibility risk
- benchmark requirement
- implementation owner
- deadline
- evidence link

The first tracked domains are model serving, model compatibility, MCP, memory stores, distributed execution, security boundaries, local inference, and agent orchestration.

## Move I — Consolidate repository governance

Immediate governance work:

- archive zero-byte stale repositories
- distinguish canonical, satellite, experiment, generated, and deprecated repositories
- add CODEOWNERS to canonical repositories
- add security policy and disclosure process
- add release and versioning rules
- add required CI checks
- add architecture decision records
- add claim status labels

No new repository should be created unless it has a registry entry, declared parent system, lifecycle class, and exit condition.

## Move J — Establish alpha release gates

A system reaches alpha only when it has:

- a documented installation path
- a deterministic demo path
- tests in CI
- a threat model
- explicit limitations
- rollback or cleanup instructions
- evidence bundle generation
- screenshots or video of the actual run
- a machine-readable release manifest

## Program success metrics

- one command launches the alpha stack
- one phone can discover and approve a governed tool call
- one end-to-end workflow produces a durable evidence bundle
- all public claims map to evidence or are labeled research/planned
- every canonical repository has CI, status, owner, and lifecycle metadata
- the portfolio homepage is generated from the registry
- no high-impact tool can execute without authenticated identity and bound approval
